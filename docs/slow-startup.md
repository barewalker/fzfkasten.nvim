# nvim の起動が遅い件 — 調査の指示書

**nvim の起動に 1 秒以上かかる。** ホストで起こしたときの方が顕著。まだ直っていない。
この文書だけで調べられるように書いてある。

## 測って分かっていること

`--headless` と擬似端末ありで、17 倍の差がある。

| 測り方 | ホスト (Ubuntu) | distrobox (Arch) |
|---|---|---|
| `nvim --headless --startuptime … +q` | **72 ms** | 76 ms |
| `script -qec 'nvim +q' /dev/null` (擬似端末あり) | **1.2〜1.3 秒** | 1.2 秒 |

**設定とプラグインの読み込みは原因ではない。** `--startuptime` の内訳は 72 ms で終わって
いて、ホストと容器で差もない。差は**端末とのやりとり**にある。

nvim は起動時に端末へ問い合わせを投げ、**返事を待つ**。

- 装置属性 (`CSI c` / DA1)
- 背景色 (`OSC 11`)
- 拡張鍵盤プロトコルの可否 (`CSI ? u`)
- 端末機能の問い合わせ (XTGETTCAP)

返事が来ない相手だと、諦めるまでの待ちがまるごと乗る。上の `script` の擬似端末は
**一切答えない**ので、待ちが最大に出た形。実際の kitty は答えるので、ここまでは
掛からないはず。ただし経路が長いほど往復が伸びる。

```
kitty  →  herdr  →  ttyskk  →  nvim
```

## 測り方

`time nvim +q` を三通りで打ち、差を見る。**素の kitty から始めて一層ずつ足す**。

1. **素の kitty** (herdr も ttyskk も無し) — 基準値。ここが遅ければ nvim 側の話
2. **kitty + herdr** — 1 との差が herdr の分
3. **kitty + herdr + ttyskk** — 2 との差が ttyskk の分

内訳が要るなら `--startuptime` も併せて取る。ただし上のとおり、そこには**端末の返事
待ちが出てこない**ことに注意する。

問い合わせと返事そのものを見たいなら、ttyskk の記録が使える。

```sh
env -u TTYSKK_ACTIVE TTYSKK_DEBUG=/tmp/nvim.log ttyskk -- nvim
```

`端末→ttyskk` と `ttyskk→子` の行に、問い合わせと返事が 16 進で残る。**投げてから
返事までの間隔**が分かるので、どの問い合わせで待っているかを特定できる。

## 疑っている筋

### 1. どこかの層が問い合わせに答えていない

多重化器は端末への問い合わせを自分で受けて答えることがある。答えないまま素通しすると、
往復が二重になるか、返事が返らずに timeout まで待つ。herdr がどう扱っているかを見る。

### 2. 経路が長いぶんの往復

一層ごとに読み書きが挟まる。これは構造的なもので、劇的には減らせない。**ただし
1 秒は大きすぎる**ので、これだけでは説明が付かない見込み。

### 3. nvim 側で問い合わせを減らせるか

`vim.o.ttimeoutlen` や、拡張鍵盤プロトコルの要求をやめる設定で待ちが減るか試す。
減るなら、その問い合わせの返事が来ていないことになる。

## 追わないと決めたもの

- **ttyskk の起動時のカーソル位置の問い合わせ。** `src/main.rs` で `CSI 6n` を投げて
  最大 1.5 秒待つ作りだが、**実測では返事が来ており待っていない**。記録の
  `--- 起動 … 位置の報告 Some((13, 0))` で確認済み (`None` なら待っている)。
  そもそもこれは ttyskk の起動時であって、nvim を開くたびには起きない
- **プラグインの遅延読み込みの調整。** `--startuptime` が 72 ms なので、削っても
  効かない
